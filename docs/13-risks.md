# Риски и сознательные упрощения

## Риски реализации

| Риск | Вероятность | Смягчение |
|---|---|---|
| **Ресурсы локальной машины.** Полный стенд — 10 подов приложения, Kafka, PostgreSQL, Redis, Prometheus, Grafana, Tempo, Loki — это порядка 7–9 ГБ RAM | высокая | Namespace разворачиваются раздельно; на `kind` реплики снижаются до 1, у gateway, booking и catalog — до 2; наблюдаемость поднимается отдельным профилем по необходимости. Замер 03.10.2026: узел `kind` со всеми тремя namespace после seed — 4,7 ГБ, плюс Docker и WSL. Комфортный минимум машины — 16 ГБ |
| **Медленный диск под etcd** (WSL, ноутбук). Запись в etcd по 150–450 мс, истекают lease'ы controller-manager и scheduler, оба перезапускаются, helm падает с `etcdserver: request timed out` | высокая на WSL | etcd узла `kind` в tmpfs (`deploy/kind/cluster.yaml`); стенд и так без персистентности. После перезапуска Docker кластер пересоздаётся: `make kind-down kind-up` |
| **Таймзоны и переход на летнее время.** Разворачивание локального шаблона в UTC даёт несуществующие и удвоенные часы | средняя | Отдельные unit-тесты на даты перехода; вся арифметика — на стороне PostgreSQL через `AT TIME ZONE`, не в Python |
| **Генерируемый столбец `occupied_range`** может не пройти проверку `IMMUTABLE` | **сбылся** | Не прошёл (`timestamptz + interval` — `STABLE`). Принят запасной вариант: обычный столбец, заполняемый моделью, плюс `CHECK` с тем же выражением — см. [05-data-model.md](05-data-model.md#почему-occupied_range--не-генерируемый-столбец) |
| **Объём проекта.** Десять этапов, около двух месяцев вечерами | средняя | Каждый этап заканчивается работающим состоянием; порядок отказа зафиксирован (см. ниже), ядро не режется никогда |
| **Дублирование конфигурации** между docker-compose и Helm | высокая | Единый источник переменных в `.env.example` и общий образ; расхождения ловятся обязательным прогоном в `kind` перед закрытием этапа |
| **Telegram требует токен бота** от BotFather и доступ к API | низкая | Адаптер выбирается конфигурацией; при отсутствии токена работает лог-провайдер, функциональность системы не страдает |
| **Гонка keep-alive на гейтвее.** Прокси не ретраит; запрос, ушедший по простаивающему соединению в момент, когда завершающийся под его закрывает, получит `503` | низкая | Пауза `preStop` уводит новые соединения раньше; в прогоне на `kind` (удаление пода `booking` под нагрузкой, keep-alive-клиент) ошибок 0 из ~7600. Эксперимент T9.4 через гейтвей и Traefik (16.10.2026): удаление подов `booking` и `api-gateway` и rolling update обоих под 50 RPS — 0 ошибок из ~33 500 запросов; повтор на стороне прокси не понадобился |
| **Остановка Redis под нагрузкой.** Каждая операция кэша и лимитера ждёт таймаут, CPU и соединения уходят в ожидание, предохранители между сервисами размыкаются | **сбылся** (16.10.2026: 56 % ошибок) | Общий предохранитель кэша и лимитера (3 сбоя → 5 с без Redis) и HPA у `catalog`; повтор — 0 ошибок ([16-failure-drills.md](16-failure-drills.md)) |
| **Kafka в KRaft на одной реплике** может капризничать при рестартах кластера | низкая | В `kind` лог Kafka на PVC: остановка брокера на 5 минут под нагрузкой прошла без потерь и дублей (16-failure-drills.md). В compose персистентности нет: пересоздание топиков — часть перезапуска стенда, состояние системы от этого не страдает благодаря outbox |

## Порядок отказа при нехватке времени

Режется строго в этом порядке, слева направо:

```
Telegram-адаптер → Loki и логи → Tempo и трейсы → HPA и PDB → schemathesis → k6
```

Всё, что относится к `booking`, Kafka, outbox и инварианту непересечения,
не режется никогда — это ядро проекта.

## Сознательные упрощения относительно продакшена

- Kafka, PostgreSQL и Redis — по одной реплике, без персистентности (кроме лога Kafka в `kind`)
  и без резервного копирования
- Нет Schema Registry: совместимость схем событий держится на общей библиотеке
  и дисциплине
- Нет автоскейла консьюмеров по лагу (KEDA), нет chaos-инжиниринга —
  отказы проверяются вручную
- Секреты в k8s Secret без шифрования в git (нет Sealed Secrets / Vault)
- Нет мультирегиональности, реплик для чтения, партиционирования таблицы броней
  по времени
- Оффлайн-клиент записывается администратором на его собственную учётную запись —
  отдельной сущности «гость» нет
- Нет облачного деплоя: критерий готовности — локальный `kind`

## Что станет узким местом при росте нагрузки

Не проблема на целевых 50 RPS, но полезно понимать заранее:

| Компонент | Предел | Что делать при росте |
|---|---|---|
| Запрос доступности | Тяжёлый `generate_series` по широкому диапазону дат | Ограничить диапазон, поднять TTL кэша, вынести чтение на реплику |
| Таблица `bookings` | Растёт бесконечно, gist-индекс раздувается | Партиционирование по месяцу `start_at`, архивация прошлых периодов |
| Outbox-relay | Один поток на реплику | `FOR UPDATE SKIP LOCKED` уже позволяет масштабировать репликами |
| Партиции Kafka | 3 партиции ограничивают параллелизм консьюмеров | Увеличить число партиций (ключ агрегата сохраняет порядок) |

## Политики салона применяются в booking с задержкой

У салона нет событий: `catalog.masters.v1` и `catalog.services.v1` описывают мастеров
и услуги. Поэтому смена `slot_step_min`, отступа, горизонта или дедлайна отмены салона
доходит до `booking` только по истечении TTL кэша ответа `catalog` — до 5 минут.
Таймзона — исключение: её смена публикует `master.updated` на каждого мастера салона.
Сознательное упрощение: политики меняются редко и администратором, а цена
отдельного топика `catalog.salons.v1` — ещё один продюсер, консьюмер и схема.
Если задержка станет проблемой, решение — событие `salon.updated`, которое
увеличивает поколения мастеров салона.
