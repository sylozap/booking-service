# Журнал принятых решений

Результат девяти блоков проектирования. Каждое решение принято явно;
обоснования ключевых — в [adr/](adr/README.md).

## Блок 1. Домен и объём

- Сеть салонов → мастера → услуги; мультиарендность на уровне салона.
- Роли: `client`, `master`, `salon_admin`, `super_admin`.
- Единый `user`, роли и профили отдельно; человек может быть и клиентом, и мастером.
- Регистрация обязательна: телефон + email, пароль, подтверждение email, доступ по JWT.
- Услуга принадлежит салону (базовая цена + длительность), мастер может переопределить
  цену и длительность под себя.
- MVP: каталог, график мастера, расчёт слотов, создание/отмена/перенос записи, просмотр
  записей по ролям, уведомления, напоминание за N часов, отметки `completed` / `no_show`.
  *(Реализовано без `/auth/me`: смены контактов и деактивации аккаунта нет — уточнение 13.)*
- Вне скоупа: отзывы и рейтинг, онлайн-оплата, лояльность, зарплаты, склад,
  запись на несколько услуг одним визитом.
- Уведомления: абстракция провайдера + адаптеры «лог-заглушка» и Telegram.
  Канал email есть, но всегда уходит в лог-провайдер.

## Блок 2. Правила записи

- График мастера: недельный шаблон + исключения на конкретные даты.
- Сетка старта — 15 минут, шаг настраивается на салон; длительность произвольная.
- Буфер после записи на уровне мастера (по умолчанию 0); перерывы — через исключения.
  Занятость = длительность + буфер.
- Окно бронирования: не раньше 2 ч до начала, горизонт 60 дней; отмена/перенос клиентом
  не позже 4 ч; все пороги — настройки салона.
- Овербукинг запрещён: интервалы записей одного мастера не пересекаются.
- Гонка: побеждает первый коммит, арбитр — ограничение PostgreSQL; проигравший получает
  `409` и список ближайших свободных слотов.
- Время: всё в UTC (`timestamptz`), у салона IANA-таймзона, расписание задаётся в
  локальном времени салона.
- Статусы: `pending` → `confirmed` (автоматически) → `completed` / `no_show` /
  `cancelled_by_client` / `cancelled_by_salon`.

## Блок 3. Границы сервисов

- Пять сервисов: `api-gateway`, `auth`, `catalog`, `booking`, `notification`.
- `booking` владеет графиком, бронями и расчётом доступности — инвариант атомарен.
  Отдельный `scheduling` отклонён.
- Доступность считается SQL-запросом на лету, без материализованных слотов.
- `catalog` владеет салонами, мастерами (профиль), услугами и привязкой мастер × услуга;
  `booking` хранит `salon_id` / `master_id` как ссылки без FK, валидирует их синхронно
  и сохраняет снимок услуги в брони.
- Разделение мастера: «кто он и что предлагает» — в `catalog`, «когда работает и кто
  занят» — в `booking`.
- `auth` выпускает JWT RS256; gateway проверяет подпись и прокидывает identity-заголовки,
  сервисы умеют проверять сами через JWKS. Keycloak отклонён.
- `notification` держит собственную таблицу контактов, наполняемую событиями из `auth`.
- Монорепозиторий, образ на сервис, общая библиотека `libs/common`.

## Блок 4. Данные и консистентность

- Один инстанс PostgreSQL, отдельная база и пользователь на сервис.
- Инвариант непересечения — частичный `EXCLUDE USING gist` по активным статусам.
- Transactional outbox + собственный relay-воркер; Debezium отклонён.
- Идемпотентность: `Idempotency-Key` + таблица `idempotency_keys`.
- Redis: кэш каталога (TTL 5 мин), кэш доступности (TTL 60 с), rate limiting.
  Кэш доступности не является арбитром. *(Дополнено: предохранитель к Redis —
  уточнение 10.)*
- Саги нет.
- Удалений нет, только мягкая деактивация; `master.deactivated` → отмена будущих броней
  и уведомления клиентам.

## Блок 5. Kafka и события

- Топики по агрегату с версией в имени: `auth.users.v1`, `catalog.masters.v1`,
  `catalog.services.v1`, `booking.bookings.v1`, `booking.reminders.v1`, плюс `<topic>.dlq`.
- Ключ = id агрегата, 3 партиции, RF=1 на локальном стенде.
- JSON + Pydantic-схемы событий в `libs/common`, клиент `aiokafka`.
  Schema Registry и FastStream отклонены.
- Единый конверт события; ломающее изменение схемы → новый топик `.v2`.
- At-least-once, ручной коммит после обработки, дедупликация через `processed_events`
  в одной транзакции с эффектом.
- Ретраи: 3 попытки с экспоненциальной задержкой → DLQ; невалидные сообщения уходят
  в DLQ сразу, без ретраев.
- Напоминания: планировщик внутри `booking`, скан раз в минуту, публикация через outbox.

## Блок 6. API-контур

- `api-gateway` на FastAPI: JWT, rate limiting, correlation-id, проксирование;
  снаружи — Ingress. Гейтвей тонкий, единственное исключение — агрегирующий эндпоинт
  карточки мастера.
- URL: `/api/v1/<ресурс>`, версия общая для системы.
- Ошибки — RFC 9457 `problem+json` с доменным `code`; списки — курсорная пагинация.
- Access-JWT 15 мин RS256; refresh 30 дней с ротацией и детекцией повторного
  использования, хеши в БД `auth`; отзыв и «выйти со всех устройств»;
  подтверждение email одноразовой ссылкой.
- Rate limiting на гейтвее, sliding window в Redis, отдельные лимиты для анонимов,
  авторизованных и дорогих операций.
- Реалтайма нет: HTTP-опрос + кэш 60 с + `409` при гонке.
- Межсервисно — HTTP через `httpx` с таймаутами, ретраями и circuit breaker;
  сервисный JWT (client credentials) от `auth`.

## Блок 7. Инфраструктура и деплой

- Локально: `docker-compose` для разработки + `kind` для проверки k8s-развёртывания.
- Деплой: Helm, один параметризуемый chart на сервис, values по окружениям.
- Инфраструктура в кластере: собственный chart `infra` на тех же образах, что
  в compose (PostgreSQL, Redis, Kafka в режиме KRaft), одна реплика, без персистентности
  локально. Изначально — Bitnami-чарты, заменены 02.10.2026, см. уточнение 3.
  *(Пересмотрено: лог Kafka в `kind` — на PVC, уточнение 11.)*
- Миграции: Helm-хук `pre-install`/`pre-upgrade` → k8s Job; приложение при старте
  проверяет версию схемы и падает при несовпадении.
- Конфигурация: `pydantic-settings` + ConfigMap, секреты — k8s Secret,
  в git только `.env.example`.
- Надёжность: startup/liveness/readiness пробы, graceful shutdown по SIGTERM,
  requests/limits, HPA для `api-gateway` и `booking`, PDB, 2 реплики stateless-сервисов.
  KEDA — вне скоупа. *(Пересмотрено: HPA и у `catalog`, в `kind` минимум 2 пода у
  gateway, booking и catalog — уточнения 9 и 12.)*
- CI: GitHub Actions (ruff → mypy → pytest+testcontainers → образы → GHCR по SHA),
  зависимости на `uv`. *(Дополнено: jobs `fuzz`, `alerts`, `helm`; push только с `main`.)*

## Блок 8. Наблюдаемость и надёжность

- `kube-prometheus-stack`, `/metrics` через инструментатор, сбор по ServiceMonitor.
- Метрики: RED по HTTP + доменные (брони, конфликты слотов, длительность запроса
  доступности, outbox, лаг консьюмера, DLQ, уведомления, планировщик).
- OpenTelemetry с автоинструментацией FastAPI / httpx / SQLAlchemy / aiokafka / Redis
  → Tempo; trace-контекст протаскивается через заголовки Kafka.
- `structlog`, JSON в stdout, Alloy → Loki, связка трейс ↔ логи по `trace_id`.
- Сквозной `X-Correlation-Id` через `contextvars` → HTTP → конверт события → Kafka.
- Три дашборда как код, алерты в Alertmanager, SLO зафиксированы.
- Тесты: unit на домен, интеграционные на testcontainers, API-тесты, тест гонки за слот,
  schemathesis; покрытие домена 80%+.
- Нагрузочный сценарий на k6 + ручные эксперименты на отказы.

## Блок 9. Нефункциональные требования

- Условная нагрузка: 20 салонов, 200 мастеров, 50 000 клиентов, 2 000 записей в день,
  пик 50 RPS (80% — чтение доступности).
- Темп: несколько вечеров в неделю, 1,5–2 месяца, 10 этапов.
- Готовность: всё поднимается в локальном `kind`, демо-сценарий проходит end-to-end,
  дашборды показывают живые данные, CI зелёный. Облачный деплой вне скоупа.
- Приоритеты обучения: все четыре направления (асинхронка, Kubernetes, наблюдаемость,
  backend-глубина) — ничего не режем.
- Язык: код, комментарии, коммиты, OpenAPI — английский; документация и ADR — русский.
- Режим работы: этап за этапом, с объяснением ключевых решений по ходу;
  домен покрывается тестами до реализации, инфраструктурный код — после.
- Демо-данные: seed-скрипт (3 салона, 12 мастеров, 15 услуг, графики на месяц,
  100 клиентов, случайные брони), запускается командой и k8s Job'ом.

## Уточнения, внесённые при сборке документа

Приняты 02.09.2026 вместе с архитектурой.

1. **`master_services` живёт в `catalog`, а не в `booking`.** В блоке 3 было
   зафиксировано «переопределения услуг — в `booking`», но цена принадлежит витрине:
   иначе запрос «услуги мастера с ценами» заставил бы `catalog` ходить в `booking`.
   См. [ADR-0017](adr/0017-master-services-in-catalog.md).
2. **Политики салона хранятся в `catalog`** и отдаются `booking` во внутреннем
   эндпоинте вместе с длительностью услуги — один вызов, один кэш, без второй копии.

## Уточнения, внесённые в ходе реализации

3. **Инфраструктура в кластере — свой chart вместо Bitnami** (02.10.2026, Э8).
   Bitnami перестал публиковать бесплатные версионированные образы: прежние теги
   заморожены в `bitnamilegacy` и не обновляются. Свой chart `deploy/helm/infra`
   на образах compose — около двухсот строк YAML без персистентности; compose и `kind`
   гоняют один и тот же софт, а базы и роли создаёт один скрипт
   `deploy/helm/infra/files/init-databases.sh`.
4. **Бюджет завершения пода задаётся частями** (02.10.2026, Э8). Kubernetes снимает
   удаляемый под с эндпоинтов параллельно с SIGTERM, а uvicorn перестаёт принимать
   соединения раньше, чем приложение переключает readiness. Поэтому от ошибок защищает
   пауза `preStop`, а не readiness. `terminationGracePeriodSeconds` = `preStop` +
   ожидание запросов uvicorn + остановка фоновой работы + запас; сумму считает chart.
5. **Первый `super_admin` — из конфигурации** (03.10.2026, Э8). Создать салон и
   выдать роль `super_admin` может только `super_admin`, поэтому первого через API
   не завести. auth при старте создаёт его из `BOOTSTRAP_ADMIN_EMAIL`, `_PHONE`,
   `_PASSWORD` (все три или ни одной) с подтверждённым адресом; при следующих
   стартах только проверяет роль, пароль и контакты не трогает. Тот же подход,
   что у `SERVICE_CLIENTS`: хеш пароля в миграции был бы секретом в git.
6. **Seed идёт в API сервисов, минуя гейтвей** (03.10.2026, Э8). Лимиты гейтвея
   на регистрацию и брони делают seed через него невозможным; эндпоинты те же,
   валидация и события те же — в базу seed не пишет.
7. **Ingress-контроллер в `kind` — Traefik** (03.10.2026, Э8). ingress-nginx закрыт
   в марте 2026 и не получает исправлений; Gateway API расходился бы с планом.
8. **Tempo, Loki и Alloy в кластере — свой chart на образах и конфигах compose**
   (03.10.2026, Э8), как и infra в уточнении 3; `kube-prometheus-stack` — upstream.
   Правила, дашборды и маршрутизация берутся из тех же файлов, что монтирует compose.
9. **HPA у `catalog`** (16.10.2026, Э9, `7cf2dce`). С остановленным Redis каждый
   запрос доступности идёт в `catalog`; один под упирался в лимит CPU, размыкал
   предохранитель `booking`, клиенты получали `503`. `catalog` масштабируется
   2–5 подов (в `kind` 2–3) — по часу без кэша, а не по часу с тёплым кэшем.
10. **Предохранитель к Redis у кэша и rate limiter** (16.10.2026, Э9, `a20682a`).
    Остановленный Redis давал 56 % ошибок: каждая операция ждала свой таймаут.
    Три сбоя подряд — Redis не спрашивается 5 с, операции сразу промах / пропуск.
11. **Лог Kafka в `kind` на PVC** (16.10.2026, Э9, `01e40fe`). На `emptyDir`
    остановка брокера стирала топики и offsets; эксперимент проверял бы потерю
    диска, а не простой брокера.
12. **gateway и booking в `kind` — минимум 2 пода** (16.10.2026, Э9, `dde9fdc`).
    С одним подом удаление или выкатка — простой по определению.
13. **`/auth/me` и события `user.contacts_updated`, `user.deactivated` не
    реализованы.** В план реализации не вошли: ни один сценарий их не требует.
    Контракты событий и обработчики в `notification` готовы.
14. **Периодической чистки `idempotency_keys` нет** (`990aff7`). Просроченный
    ключ удаляется при следующем обращении с ним; фоновая задача — долг.
15. **Первичные ключи — `uuid4`, а не UUIDv7.** В Python 3.12 `uuid7` нет;
    локальность индекса на целевых объёмах не измерялась.
