# Результаты нагрузочного тестирования

Прогоны 16.10.2026, ветка `feat/T9-hardening`. Сценарий —
`loadtest/k6/booking_flow.js` (T9.1), запуск — `make loadtest`.

## Условия прогона

Цифры имеют смысл только вместе с этими условиями.

| Параметр | Значение |
|---|---|
| Машина | AMD Ryzen 5 5500U (6 ядер / 12 потоков), 14 ГиБ RAM, Linux 7.0 |
| Кластер | kind 0.32, один узел, Kubernetes 1.37.0; Docker видит 12 CPU и 15 ГиБ |
| Стенд | `make kind-up OBSERVABILITY=1`: Traefik, 5 сервисов, PostgreSQL / Redis / Kafka по одной реплике, kube-prometheus-stack, Tempo, Loki, Alloy. Узел — около 4,9 ГиБ |
| Ресурсы пода сервиса | requests 100m CPU / 128 МиБ, limits 500m CPU / 384 МиБ (`deploy/helm/values/local.yaml`) |
| Автомасштабирование | gateway, booking и (после T9.6) catalog: HPA 2–3 пода, цель 70 % CPU от request. auth и notification — 1 под |
| Данные | seed: 3 салона, 12 мастеров, 15 услуг, 48 пар мастер × услуга, графики на 30 дней |
| Клиенты | 100 пользователей `load-NNN@load.barber.example`, токены выданы перед прогоном |
| Генератор | k6 1.3.0 в Docker, сеть хоста, через Ingress `barber.local` — как браузер |
| Профиль | `ramping-arrival-rate`: 0 → 50 RPS за 2 минуты, 5 минут на 50 RPS |

Генератор нагрузки и стенд делят одну машину. Цифры latency поэтому
пессимистичны в части CPU и оптимистичны в части сети (ни одного реального хопа).

## Итог по SLO

Финальная сборка ветки (все исправления ниже), прогоны `baseline` (свежие слоты)
и `final`:

| Метрика | SLO | Прогон `baseline` | Прогон `final` |
|---|---|---|---|
| Доля ошибок | < 1 % | **0 %** (0 из 18 527) | **0 %** (0 из 18 029) |
| p95 доступности (`GET /availability`) | < 1 с | **32 мс** | **21 мс** |
| p95 создания брони (`POST /bookings`) | < 500 мс | **39 мс** (512 броней) | 26 мс (16 броней*) |
| p95 карточки мастера | — | 14 мс | 14 мс |
| p95 просмотра перед записью | < 1 с | 37 мс | 26 мс |
| Конфликты `409 slot_taken` | — | 0 % | 0 % |

\* К финальному прогону слоты в окне сценария почти закончились. Сценарий
делает настоящие брони, около 500 за прогон, и p95 создания брони посчитан по
16 запросам. Представительные цифры записи — из прогона `baseline` и из прогона
эксперимента с Kafka (395 броней, p95 44 мс).

Все шесть порогов k6 зелёные, SLO подтверждены с запасом больше чем на порядок.

Серверная сторона (Prometheus, конец удержания):

- p95 запроса доступности в booking: 24 мс из базы, 10 мс из кэша. Из кэша
  отвечает около трети запросов (15 из 42 в секунду): каждая бронь сбрасывает
  поколение кэша мастера, а 48 пар × 14 дней — это 672 ключа.
- Кэш каталога в catalog: 99 % попаданий.
- CPU на 50 RPS: booking около 0,45 ядра на 3 пода, gateway около 0,34, catalog 0,06.

## Поведение HPA

- Старт: gateway и booking по 2 пода (минимум HPA в kind).
- Через 60–90 секунд разгона (около 30–35 RPS) оба выросли до 3 — максимума
  в kind.
- На удержании загрузка CPU от request держится на 113–147 % при цели 70 %:
  HPA хотел бы 5–6 подов, но упёрся в максимум 3.
- Latency при этом не страдает: request 100m — это единица учёта для HPA,
  лимит пода 500m, троттлинга на 50 RPS нет.
- Понижение после нагрузки идёт с задержкой 300 секунд (стабилизация из чарта).

Вывод: в kind HPA срабатывает и упирается в потолок, но на целевых 50 RPS
потолка хватает. В продакшене (2–5 подов, тот же request) запас по подам больше.

## Где предел

Стресс-прогон на 150 RPS (3× от пика, 1 минута разгона, 3 минуты удержания):

| | 150 RPS |
|---|---|
| Доля ошибок | 27 % — все `503` |
| p95 доступности | 3,0–3,6 с |
| CPU | gateway около 1,1 ядра на 3 пода, booking около 0,95: поды упираются в лимит 500m |

Деградация управляемая. Пул HTTP-соединений gateway к booking истекает
(`PoolTimeout`), circuit breaker открывается, клиенты быстро получают `503`.
Предел стенда в kind — между 50 и 150 RPS и определяется лимитами CPU подов,
а не архитектурой.

## Расхождения с целевыми показателями

Расхождений с SLO нет. Отличия от ожиданий документации:

- **В kind HPA упирается в максимум** уже на 50 RPS (загрузка 113–147 % от
  request). Это свойство request 100m в kind, а не нехватка мощности: лимит
  в 5 раз больше request, latency в норме.
- **Доля попаданий в кэш доступности около 36 %**, а не «большинство». Ключ кэша
  версионируется поколением мастера, и при 2,5 бронях в секунду на 12 мастеров
  поколение меняется каждые несколько секунд. SLO выполняется и без кэша:
  p95 из базы — 24 мс.
- **Цикл прогона ограничен 15 минутами** — временем жизни access-токена.
