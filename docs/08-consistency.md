# Консистентность, кэш, идемпотентность

Саги в системе нет — и это осознанный результат, а не упущение. Границы проведены так,
что ни одна бизнес-операция не требует распределённой транзакции.
См. [ADR-0003](adr/0003-no-saga.md).

## Четыре уровня гарантий

| Уровень | Механизм | Что защищает |
|---|---|---|
| 1. База | `EXCLUDE USING gist` | Непересечение броней. Единственный арбитр. Проигравший получает `409`, а не порчу данных |
| 2. Outbox | Событие пишется в ту же транзакцию, что и изменение | «Изменение есть ⇔ событие ушло». Kafka может лежать — данные не разойдутся |
| 3. Консьюмер | At-least-once + `processed_events` в одной транзакции с эффектом | Повторная доставка не даёт повторного эффекта |
| 4. Клиент | `Idempotency-Key` | Двойной клик и ретрай клиента не создают вторую запись |

## Transactional outbox

```python
# псевдокод создания брони
async with session.begin():
    booking = Booking(...)
    session.add(booking)
    session.add(
        OutboxMessage(
            topic="booking.bookings.v1",
            aggregate_type="bookings",
            aggregate_id=booking.id,
            event_type="booking.created",
            payload=...,
            correlation_id=ctx.correlation_id,
        )
    )
    session.add(IdempotencyKey(...))
# коммит: либо всё, либо ничего
```

Relay — отдельная asyncio-задача в составе того же сервиса:

1. `SELECT ... FROM outbox WHERE published_at IS NULL ORDER BY created_at
   LIMIT 100 FOR UPDATE SKIP LOCKED` — `SKIP LOCKED` позволяет нескольким репликам
   работать параллельно без дублей.
2. Публикация в Kafka с ключом агрегата.
3. `UPDATE outbox SET published_at = now()`.

При падении между шагами 2 и 3 сообщение уйдёт повторно — это at-least-once,
и его гасит дедупликация консьюмера.

Метрики: `outbox_pending_messages`, `outbox_publish_lag_seconds`.
Растущий лаг означает, что relay встал.

## Идемпотентность запросов

`POST /api/v1/bookings` требует заголовок `Idempotency-Key`.

| Ситуация | Поведение |
|---|---|
| Ключа нет в таблице | Обработка, сохранение ответа вместе с хешем тела запроса |
| Ключ есть, хеш тела совпадает | Возврат сохранённого ответа, без повторной обработки |
| Ключ есть, хеш тела другой | `422 idempotency_key_reuse` |

Запись ключа происходит в той же транзакции, что и создание брони. TTL 24 часа
(`IDEMPOTENCY_TTL_HOURS`). Периодической чистки нет: просроченная строка
удаляется при следующем обращении с тем же ключом. Таблица растёт на число
броней за сутки и дальше — до появления фоновой чистки.

## Кэш в Redis

| Ключ | Содержимое | TTL | Инвалидация |
|---|---|---|---|
| `catalog:{gen}:…` (в `catalog`) | Карточка мастера, услуга, ответ внутреннего эндпоинта | 5 мин | Любая запись в `catalog` увеличивает общее поколение |
| `booking:offering:{mid}:{sid}:{gm}.{gs}` (в `booking`) | Ответ внутреннего эндпоинта `catalog` | 5 мин | `master.updated`/`master.deactivated` увеличивают поколение мастера, `service.updated`/`service.archived` — поколение услуги |
| `booking:avail:{master_id}:{service_id}:{date}:{gm}.{gs}` | Список свободных слотов на день | 60 с | Те же поколения мастера и услуги; изменение графика и буфера увеличивает поколение мастера |
| `ratelimit:{scope}:{subject}:{window}` | Счётчики sliding window (текущее и предыдущее окно) | 2 окна | Автоматически по TTL |

Ключи `booking` не удаляются, а становятся недостижимыми: событие делает `INCR`
счётчика поколения, и ключ, записанный под старым значением, больше никто
не читает, а TTL его убирает. `service.updated` не несёт `master_id`, поэтому точечное
удаление потребовало бы искать всех мастеров услуги; счётчик услуги этого не требует.
`SCAN` и `KEYS` не используются.

> **Кэш доступности не является источником истины.** Он может отдать слот, которого
> уже нет — это допустимо и ожидаемо. Правильность обеспечивает ограничение базы
> при вставке. Не добавляйте в кэш логику «резервирования»: это была бы попытка
> заменить гарантию договорённостью. См. [ADR-0012](adr/0012-cache-is-not-arbiter.md).

Падение Redis не должно ронять систему: при недоступности кэша сервисы читают
источник напрямую, а rate limiting переходит в режим «пропускать».

## Что происходит при отказах

| Отказ | Поведение системы |
|---|---|
| Kafka недоступна | API работает полностью. Outbox копит сообщения, relay ретраится. После восстановления всё досылается. Уведомления приходят с задержкой |
| Redis недоступен | Работает, но медленнее: каждый запрос доступности идёт в БД и в `catalog`. Rate limiting отключается. Кэш и лимитер делят предохранитель: после трёх сбоев подряд Redis не спрашивается 5 с, иначе каждая операция сначала ждала бы свой таймаут (`a20682a`). Нагрузку без кэша держит HPA `catalog` (`7cf2dce`) |
| `catalog` недоступен | Создание брони невозможно (`503`). Чтение существующих броней работает — в них снимок услуги |
| `notification` недоступен | Ни на что не влияет: события лежат в Kafka и будут обработаны после подъёма |
| Реплика `booking` упала | Вторая реплика обслуживает трафик. Незакоммиченные транзакции откатываются, оффсеты не сдвинуты — сообщения обработаются заново и будут отсечены дедупликацией |

## Каскадная компенсация

Единственная цепочка, где событие меняет состояние другого сервиса:

`catalog: master.deactivated` → `booking`: пометить `master_settings.is_active = false`,
отменить будущие активные брони (`cancelled_by_salon`), положить `booking.cancelled`
в outbox на каждую → `notification`: уведомить клиентов.

Всё изменение состояния в `booking` — одна транзакция вместе с записью
в `processed_events`. Повторная доставка события безопасна: дубль отсечётся,
а брони уже в конечном статусе.

- Отменяются только `pending` и `confirmed` со `start_at > now`: прошедшие,
  идущие и закрытые визиты не трогаются.
- `cancelled_by = NULL` (отменил не человек), `cancel_reason = master_deactivated`;
  каждое `booking.cancelled` несёт `causation_id` = `event_id` события
  `master.deactivated`.
- Размер транзакции ограничен горизонтом записи, а число SQL-операторов
  от числа броней не зависит: блокировка — один `SELECT … FOR UPDATE`,
  отмена — один пакетный `UPDATE`, события — одна вставка в outbox.
