# Контекст и границы скоупа

Сеть салонов: клиент выбирает салон, мастера и услугу, видит свободные слоты
и записывается. Система гарантирует, что один мастер не окажется занят дважды.

## Акторы и роли

| Роль | Что может |
|---|---|
| `client` | Смотреть каталог и доступность, создавать / переносить / отменять свои записи, видеть свою историю |
| `master` | Всё как клиент; плюс видеть своё расписание и свои записи, отмечать `completed` / `no_show` |
| `salon_admin` | Управлять своим салоном: мастера, услуги, графики, политики; любые операции с записями своего салона; запись «оффлайн»-клиента |
| `super_admin` | Управлять салонами и назначать администраторов |

Учётная запись одна (`user`), роли назначаются отдельно и могут быть привязаны
к салону. Мастер может записаться к коллеге как обычный клиент.

Роль хранится в `auth` как строка таблицы `user_roles (user_id, role, salon_id)`.
Для `salon_admin` и `master` поле `salon_id` заполнено, для глобальных ролей — `NULL`.
Роли попадают в access-токен и проверяются как на гейтвее, так и в сервисах.

## Внутри скоупа

- Регистрация по email и телефону, пароль, подтверждение email, JWT-доступ
- Каталог: салоны, мастера, услуги, привязка «мастер × услуга» с переопределением
  цены и длительности
- График мастера: недельный шаблон, исключения (выходной, укороченный день, перерыв),
  буфер после записи
- Расчёт свободных слотов под конкретную услугу конкретного мастера
- Создание, перенос, отмена записи; статусы `completed` / `no_show`
- Уведомления о событиях записи и напоминание за 4 часа до визита: Telegram;
  канал email есть в модели, но письма уходят в лог — почтового провайдера нет
- Каскад: деактивация мастера отменяет его будущие записи и уведомляет клиентов

## Сознательно вне скоупа

- Онлайн-оплата и предоплата — именно поэтому в системе нет саги
- Отзывы и рейтинги, программа лояльности, зарплаты мастеров, склад расходников
- Запись на несколько услуг подряд одним визитом
- Овербукинг, лист ожидания, реалтайм-канал (WebSocket / SSE)
- Фронтенд — проверка через OpenAPI и HTTP-клиент
- Смена контактов и деактивация учётной записи (`/auth/me`) — контракты событий
  есть, эндпоинтов нет
- Отдельная сущность «гость»: оффлайн-клиента администратор записывает на его учётную запись

## Целевые показатели

| Параметр | Значение | Комментарий |
|---|---|---|
| Салоны / мастера / клиенты | 20 / 200 / 50 000 | Условная малая сеть |
| Записей в день | 2 000 | Пик приходится на вечер буднего дня |
| Пиковая нагрузка | 50 RPS | 80 % — чтение доступности |
| Доступность API | 99 % успешных | SLO, окно 30 дней |
| p95 создания брони | < 500 мс | Включая синхронный вызов в `catalog` |
| p95 запроса доступности | < 1 с | На запрос по одному дню |

## Критерий готовности проекта

Всё поднимается в локальном `kind` одной командой, демо-сценарий проходит end-to-end,
дашборды показывают живые данные, тесты зелёные в CI. Деплой в облако вне скоупа.
