# Эксперименты на отказ

Четыре проверки из раздела «Эксперименты на отказ» документа
[12-testing.md](12-testing.md): падение пода, rolling update, остановка Kafka,
остановка Redis. Проведены 16.10.2026 на ветке `feat/T9-hardening`.

## Методика

**Стенд и нагрузка** — те же, что в [15-load-test-results.md](15-load-test-results.md):
kind на одной машине, наблюдаемость включена, k6 через Ingress, 50 RPS
(1 минута разгона, дальше удержание). Отличие одно: `DAYS_AHEAD=28`, чтобы
сценарию хватало свободных слотов.

**Что фиксируется в каждом эксперименте:**

- отчёт k6: доля ошибок у клиента, p95 по операциям;
- таймлайн подов и HPA раз в 5 секунд (`kubectl get pods/hpa`);
- метрики Prometheus: статусы ответов по сервисам, p95, outbox, кэш, алерты;
- для Kafka — сверка баз booking и notification по идентификаторам событий.

Отказ выполняется командой в заданную секунду от старта k6.

**Критерий для всех экспериментов — ноль ошибок у клиента.** Ошибкой считается
любой ответ, кроме `2xx` и ожидаемого `409 slot_taken`, а также таймаут.

## 1. Падение пода (T9.4)

**Подготовка.** В kind у gateway и booking было по одной реплике: потеря
единственного пода — отказ по определению. Минимум HPA для них поднят до двух
(`deploy/helm/values/local.yaml`).

**Ход.** На 150-й секунде — `kubectl delete pod` одного пода `booking`, на
270-й — одного пода `api-gateway`. К этому моменту HPA держал по 3 пода.

| | booking | api-gateway |
|---|---|---|
| Удаление | 07:14:25 | 07:16:25 |
| Новый под Ready | ≤ 07:14:32 (≤ 7 с) | ≤ 07:16:36 (≤ 11 с) |
| Старый под завершён | 07:14:42 (17 с: `preStop` 5 с + дренаж) | 07:16:57 (32 с) |

**Результат.** 0 ошибок из 16 805 запросов, p95 доступности 56 мс (в покое
25–32 мс). Число реплик восстановил контроллер Deployment, а не HPA: HPA видел
то же число подов, что и раньше.

Риск «гонки keep-alive на гейтвее» из [13-risks.md](13-risks.md) не проявился:
под gateway удалялся под нагрузкой через Traefik, и ни один запрос не потерян.

## 2. Rolling update под нагрузкой (T9.4)

**Ход.** `helm upgrade --reuse-values` с новой аннотацией пода: на 120-й секунде
для `booking`, на 240-й — для `api-gateway`. Стратегия чарта —
`maxUnavailable: 0`, `maxSurge: 1`.

| | booking | api-gateway |
|---|---|---|
| `helm upgrade` | 28 с (с Job миграций, 7 с) | 103 с (из них Job seed — 82 с: хук gateway) |
| Замена трёх подов | 07:31:56 → 07:32:53 | 07:33:45 → 07:34:43 |

**Результат.** 0 ошибок из 16 772, ни одного `502`/`503`/`504`. p95 доступности
47 мс.

Первая попытка этого эксперимента не состоялась: ключ аннотации с точкой
потерял экранирование, и helm отклонил патч ещё до изменения подов. В отчёт
не входит.

## 3. Остановка Kafka (T9.5)

**Подготовка.** Лог Kafka в kind лежал в `emptyDir`.
`kubectl scale statefulset kafka --replicas=0` стирал вместе с подом топики
и offsets групп, и после подъёма сервисы не могли публиковать, пока топики
не созданы заново. Тогда эксперимент проверял бы потерю диска, а не простой
брокера. Лог переведён на PVC (`kafka.persistence`, в kind включается
`scripts/infra_up.sh`).

**Ход.** 12 минут нагрузки; Kafka остановлена с 07:40:44 до 07:45:44
(`kubectl scale statefulset kafka -n barber-infra --replicas=0`, затем `=1`).

**Что происходило:**

| Время | `outbox_pending_messages` (booking) | `outbox_publish_lag_seconds` | Алерт `OutboxNotDraining` |
|---|---|---|---|
| 07:40:30 | 1 | 0,2 | — |
| 07:41:30 | 31 | 40 | pending |
| 07:43:30 | 115 | 160 | pending |
| 07:45:30 | 187 | 280 | **firing** |
| 07:46:00 | 205 (пик) | 310 (пик) | firing |
| 07:46:30 | 1 | 0,1 | resolved |

- API работал полностью: 0 ошибок из 34 910, p95 доступности 28 мс, p95 записи 44 мс.
- Ни один под не перезапустился: пробы готовности от Kafka не зависят.
- Отправка уведомлений встала на время простоя и после подъёма догнала
  всплеском до 290 в минуту. Очередь outbox рассосалась примерно за 45 секунд.
- Алерт сработал. Это `OutboxNotDraining` (лаг > 30 с в течение 4 минут), а не
  порог на `outbox_pending_messages`, как было в плане: почему порог на число
  сообщений отвергнут, объяснено в правилах алертов.

**Сверка.** Брони клиентов нагрузки → события `booking.created` в outbox
booking → строки `notifications` в notification, по `event_id`:

| Окно | Броней | Событий | Уведомлений `sent` | Без уведомления | С дублем |
|---|---|---|---|---|---|
| Весь прогон, 07:38:44–07:51:00 | 395 | 395 | 395 | 0 | 0 |
| Только простой, 07:40:44–07:45:44 | 197 | 197 | 197 | 0 | 0 |

После прогона в outbox booking нет неопубликованных строк, а число записей
`processed_events` группы `notification.bookings` (2393) равно числу всех
событий outbox booking. Каждое событие обработано ровно один раз.

**Вывод.** Ни одно событие не потеряно и не продублировано. Без outbox брони,
созданные за пять минут простоя, остались бы без уведомлений. Из теории
[ADR-0004](adr/0004-transactional-outbox.md) стал наблюдаемым фактом.

## 4. Остановка Redis (T9.6)

**Ход.** 8 минут нагрузки; Redis остановлен на 4 минуты
(`kubectl scale deployment redis -n barber-infra --replicas=0`, затем `=1`).
Эксперимент проведён трижды: первые два прогона нашли две проблемы.

| Прогон | Что было в коде | Ошибки у клиента | p95 доступности (k6) |
|---|---|---|---|
| 1 | как было | **56 %** (12 744 из 22 561) | 5,4 с |
| 2 | + circuit breaker к Redis | **14 %** (3 247 из 22 598) | 1,5 с |
| 3 | + HPA у catalog | **0 %** (0 из 22 571) | 45 мс |

**Прогон 1: каждая операция ждала свой таймаут.** Подключение к Service без
эндпоинтов не отвергается, а висит до таймаута клиента (0,2 с). Запрос
доступности делает четыре операции с кэшем, catalog — ещё одну-две.

- catalog за 6 минут записал 5 350 предупреждений «cache is unavailable»,
  упёрся в CPU, исчерпал пул БД и начал проваливать готовность.
- booking ждал кэш и медленный catalog, circuit breaker booking → catalog открылся.
- Клиенты получили `503` и `504`.

Данные при этом не искажались: любая ошибка Redis — промах, Redis ни для чего
не был источником истины. Но [ADR-0012](adr/0012-cache-is-not-arbiter.md)
обещает, что без кэша система медленнее, а не неисправна.

*Исправление:* у кэша (`barber_common.cache`) и у rate limiter gateway появился
circuit breaker, тот же `CircuitBreaker`, что у межсервисных вызовов. После трёх
ошибок подряд Redis не опрашивается 5 секунд, операция сразу промах (метрика
`cache_operations_total{outcome="bypassed"}`), лимитер сразу пропускает запрос.

**Прогон 2: catalog не выдерживает трафик без кэша.** Breaker работал: операции
шли как `bypassed`, таймаутов почти не осталось. Но без кэша каждый запрос
доступности booking спрашивает catalog о мастере и услуге — около 50 запросов
в секунду в базу catalog. Единственный под catalog в kind упирался в лимит CPU
500m, отвечал секундами, и breaker booking → catalog снова открывался.

*Исправление:* у catalog появился HPA, как у booking: 2–5 подов, в kind 2–3.
catalog стоит на пути каждого запроса доступности, когда кэша нет, и должен
быть рассчитан на этот час, а не только на тёплый кэш.

**Прогон 3: итог.**

| Окно | p95 запроса доступности (booking) | p95 gateway | p95 catalog |
|---|---|---|---|
| До простоя (2 мин) | 23 мс | 26 мс | 9 мс |
| Во время простоя (3 мин) | 46 мс | 52 мс | 24 мс |
| После подъёма (1,5 мин) | 19 мс | 25 мс | 5 мс |

- **0 ошибок** из 22 571.
- **Деградация только по скорости:** p95 вырос вдвое и остался в 20 раз ниже SLO.
- **Rate limiting отключился:** за прогон ни одного `429`. В логе gateway —
  по одному предупреждению на открытие breaker (около 56 записей на под за
  4 минуты) вместо записи на каждый запрос.
- **HPA catalog** во время простоя вырос с 2 до 3 подов.
- **После подъёма Redis** breaker закрылся на первой же пробе, попадания в кэш
  вернулись в течение минуты.

## Что изменилось в проекте по итогам

| Изменение | Коммит |
|---|---|
| gateway и booking в kind — минимум 2 пода | `feat(deploy): the gateway and booking keep two pods in kind` |
| Лог Kafka на PVC в kind | `feat(deploy): the log of Kafka survives a stopped broker in kind` |
| Circuit breaker к Redis у кэша и rate limiter | `fix(common): a stopped Redis is left alone instead of waited on` |
| HPA у catalog | `feat(deploy): catalog scales with the traffic like booking` |

## Как повторить

```bash
make kind-up OBSERVABILITY=1
make loadtest DAYS_AHEAD=28 RAMP=1m HOLD=5m      # в другом терминале — отказ:
kubectl delete pod -n barber <pod booking>
helm upgrade booking deploy/helm/service -n barber --reuse-values \
    --set-string podAnnotations.drill-rollout=$(date +%s) --wait
kubectl scale statefulset kafka -n barber-infra --replicas=0   # и обратно =1
kubectl scale deployment redis -n barber-infra --replicas=0    # и обратно =1
```

Длительность прогона с отказом — не больше 15 минут (время жизни access-токена).
