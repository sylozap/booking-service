# Тестирование

| Уровень | Что покрывает | Инструмент |
|---|---|---|
| Unit | Разворачивание шаблона графика, нарезка слотов, правила отмены и переноса, политики салона — чистые функции без БД | pytest |
| Интеграционные | Репозитории, `EXCLUDE`-констрейнт, outbox и relay, дедупликация консьюмеров, кэш и его инвалидация | pytest + testcontainers (PostgreSQL, Redis, Kafka) |
| API | Контракты эндпоинтов, права по ролям, формат ошибок, идемпотентность | `httpx.AsyncClient` |
| **Тест гонки** | N параллельных запросов на один слот → ровно один `201`, остальные `409` | `asyncio.gather` + реальная БД |
| Фаззинг | Соответствие OpenAPI, обработка граничных значений | schemathesis |
| Нагрузка | Сценарий «поиск слотов → запись», 50 RPS, проверка SLO (`loadtest/k6/booking_flow.js`, `make loadtest`) | k6 |
| Отказы | Под, rolling update, Kafka, Redis под нагрузкой | kubectl вручную |
| Сквозные и инфраструктурные | Напоминание от брони до отправки (`tests/e2e`), сводный OpenAPI и метрики (`tests/contract`), секреты и chart (`tests/deploy`), seed (`tests/seed`), ссылки документации (`tests/docs`) | pytest |

Целевое покрытие доменного слоя — 80 %+. Инфраструктурный код тестами не догоняем.
Порядок написания: домен покрывается тестами **до** реализации, инфраструктурный
код — после.

## Тест гонки — главная проверка проекта

Именно он доказывает, что центральный инвариант системы работает. Без него все
рассуждения о `EXCLUDE`-констрейнте остаются рассуждениями.

```python
async def test_only_one_booking_wins(client, master, service, slot):
    results = await asyncio.gather(
        *[
            client.post(
                "/api/v1/bookings",
                json={"master_id": master.id, "service_id": service.id, "start_at": slot},
                headers={"Idempotency-Key": str(uuid4())},
            )
            for _ in range(20)
        ],
        return_exceptions=True,
    )

    created = [r for r in results if r.status_code == 201]
    conflicts = [r for r in results if r.status_code == 409]

    assert len(created) == 1
    assert len(conflicts) == 19
    assert all(r.json()["code"] == "slot_taken" for r in conflicts)
    # и в базе ровно одна активная бронь на этот слот
```

Тест обязан идти против настоящего PostgreSQL из testcontainers.
С моками он ничего не проверяет.

## Что ещё обязательно покрыть

- **Таймзоны:** слоты в салоне `Asia/Yekaterinburg`, даты перехода на летнее время,
  сутки с 23 и 25 часами.
- **Буфер:** запись 10:00–10:45 с буфером 15 мин делает 10:45 недоступным,
  но 11:00 — доступным.
- **Исключения графика:** `day_off` полностью убирает день; `custom_hours`
  перекрывает шаблон; `break` вырезает середину.
- **Идемпотентность:** повтор с тем же ключом и телом → тот же ответ и одна запись;
  повтор с другим телом → `422`.
- **Дедупликация консьюмера:** одно и то же событие дважды → один эффект.
- **Outbox:** падение между коммитом транзакции и публикацией → сообщение
  всё равно уходит после рестарта.
- **Права:** клиент не видит и не отменяет чужие записи; мастер не правит чужой график.
- **Дедлайны:** отмена за 3 часа при пороге 4 → `422`; та же отмена админом → `200`.

## Нагрузочный сценарий (k6)

```
80 %  GET /api/v1/availability   — случайный мастер, услуга, день
15 %  GET /api/v1/masters/{id}/card
 5 %  POST /api/v1/bookings      — на первый свободный слот
```

Профиль: разгон до 50 RPS за 2 минуты, удержание 5 минут.
Критерии прохождения: доля ошибок < 1 %, p95 доступности < 1 с,
p95 создания брони < 500 мс.

## Эксперименты на отказ

Проводятся вручную под нагрузкой k6; результаты — [16-failure-drills.md](16-failure-drills.md),
нагрузка — [15-load-test-results.md](15-load-test-results.md):

1. `kubectl delete pod booking-...` — запросы не теряются, вторая реплика подхватывает,
   HPA возвращает число подов.
2. `kubectl scale statefulset kafka --replicas=0` — API продолжает работать,
   `outbox_pending_messages` растёт. После подъёма Kafka очередь рассасывается,
   уведомления доходят, дублей нет.
3. `kubectl scale deployment redis --replicas=0` на 4 минуты — доступность
   считается медленнее, ошибок нет. Первые прогоны дали 56 % и 14 % ошибок;
   исправлено предохранителем к Redis и HPA у `catalog`.
4. Rolling update `booking` под нагрузкой — ни одного `502`.

Эти четыре проверки доказывают, что outbox, пробы и graceful shutdown
не декоративны.
