# ADR-0012. Кэш доступности не является источником истины

**Статус:** принято, 02.09.2026; пересмотрено 17.10.2026 — механизм инвалидации

## Контекст

Запрос доступности — самый горячий эндпоинт: 80 % трафика. Он кэшируется в Redis
на 60 секунд. Возникает соблазн пойти дальше и использовать Redis для
«резервирования» слота на время оформления записи.

## Решение

Кэш доступности хранит только результат чтения и живёт 60 секунд. Он **может отдать
слот, которого уже нет** — это допустимое и ожидаемое поведение. Правильность
обеспечивает исключительно ограничение базы при вставке
([ADR-0002](0002-exclude-constraint-as-arbiter.md)).

Инвалидация: любое событие `booking.*` по этому мастеру и дню, а также изменение
графика, удаляют ключ `avail:{master_id}:{service_id}:{date}`.

## Альтернативы

**Резервирование слота в Redis на время оформления.** Убрало бы часть конфликтов,
но ввело бы второе, слабое место принятия решения о занятости. При падении Redis
или расхождении TTL система начала бы вести себя непредсказуемо, а инвариант
перестал бы быть выразимым одним предложением.

**Не кэшировать доступность вовсе.** Меньше рассинхрона, но самый горячий эндпоинт
бил бы в базу на каждый запрос.

## Последствия

- Клиент иногда получает `409 slot_taken` — это нормальная часть протокола,
  а не ошибка; ответ содержит список ближайших альтернатив
- Метрика `booking_conflicts_total` служит индикатором качества кэша: её рост
  означает, что TTL великоват для текущей нагрузки
- Падение Redis не ломает корректность: система читает базу напрямую
- В коде не должно появляться ни одной ветки, где решение о занятости
  принимается по данным Redis

## Пересмотр (17.10.2026)

**Что изменилось.** Ключ не удаляется, а становится недостижимым: он несёт поколения
мастера и услуги — `booking:avail:{master_id}:{service_id}:{date}:{gm}.{gs}`.
Счётчик мастера (`booking:generation:master:{id}`) увеличивают пути записи
`booking` после коммита — создание, отмена, перенос, график, буфер — и консьюмер
`catalog.masters.v1`; счётчик услуги — консьюмер `catalog.services.v1`. Сбрасываются
сразу все дни мастера, а не один; события `booking.*` для этого не читаются.

**Почему** (`93114b7`, `2c42514`, `b874fa0`). `service.updated` не несёт `master_id`:
точечное удаление потребовало бы искать всех мастеров услуги или `SCAN` по ключам.
Один `INCR` дешевле, а пересчёт суток мастера после сброса — один SQL-запрос.
Читать собственные события, чтобы сбросить кэш, который можно сбросить в той же
операции, — лишняя задержка.

**Дополнено.** Падение Redis корректность по-прежнему не ломает, но оказалось
дорогим по нагрузке (16-failure-drills.md, 56 % ошибок): каждая операция ждала
таймаут. Кэш и лимитер теперь делят предохранитель — 3 сбоя подряд, 5 с без Redis
(`a20682a`), а `catalog`, на который ложится весь поток без кэша, получил HPA (`7cf2dce`).
