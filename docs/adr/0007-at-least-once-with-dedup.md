# ADR-0007. At-least-once + таблица processed_events

**Статус:** принято, 02.09.2026

## Контекст

Kafka даёт at-least-once по умолчанию: после сбоя консьюмер перечитает сообщения,
оффсет по которым не был закоммичен. Обработка должна быть устойчива к дублям,
иначе клиент получит два одинаковых уведомления, а бронь будет отменена дважды.

## Решение

At-least-once с ручным коммитом оффсета **строго после** успешной обработки.
Дедупликация — таблица `processed_events (event_id, consumer_group)`. Запись в неё
и бизнес-эффект происходят в одной транзакции:

```python
async with session.begin():
    if await already_processed(event.event_id, group):
        return
    await handle(event)
    await mark_processed(event.event_id, group)
await consumer.commit()
```

Это даёт эффективный exactly-once на стороне эффекта без транзакций Kafka.

## Альтернативы

**Kafka-транзакции (exactly-once semantics).** Красиво в теории, но EOS покрывает
только путь «Kafka → Kafka» и не распространяется на внешние эффекты: отправку
в Telegram, запись в чужую БД. Дедупликация всё равно понадобится.

**Идемпотентность по бизнес-ключу** («уведомление о брони X типа Y уже отправлено»).
Работает без служебной таблицы, но требует придумывать ключ под каждый случай
и не универсальна. Применяется дополнительно в `notification` как `dedup_key`.

**Автокоммит оффсетов.** Потеря событий при падении между коммитом оффсета
и обработкой. Неприемлемо.

## Последствия

- Дубли невидимы для бизнес-логики
- Таблица `processed_events` растёт и требует чистки по TTL (достаточно недели)
- Обработчик обязан быть транзакционным: побочные эффекты вне транзакции
  (например, HTTP-вызов) при повторе выполнятся дважды — для них нужен
  собственный ключ дедупликации
- Коммит оффсета после обработки означает, что медленный обработчик увеличивает лаг;
  лаг надо мониторить
