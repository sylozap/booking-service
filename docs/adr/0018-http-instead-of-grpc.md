# ADR-0018. HTTP вместо gRPC для внутренних вызовов

**Статус:** принято, 02.09.2026

## Контекст

Сервисы обращаются друг к другу синхронно. В системе таких путей немного:
`booking` → `catalog` за длительностью, ценой и политиками; гейтвей → все сервисы;
все сервисы → `auth` за JWKS.

## Решение

HTTP через `httpx.AsyncClient` по k8s Service DNS. Обязательная обвязка каждого
клиента: таймауты (connect и read раздельно), ретраи с экспоненциальной задержкой
и джиттером только для идемпотентных запросов, circuit breaker.

Межсервисная аутентификация — сервисный JWT по client credentials, выпускаемый `auth`.
Внутренние эндпоинты живут под префиксом `/internal/v1` и наружу не публикуются.

## Альтернативы

**gRPC для внутренних вызовов.** Быстрее, типизировано через proto, стриминг
из коробки. Но это второй транспорт, второй набор инструментов отладки и генерация
кода — при трёх синхронных путях во всей системе выигрыш не окупается.

**Доверие внутри кластера без m2m-аутентификации** (NetworkPolicy вместо токенов).
Меньше кода, но любой под в namespace может дёрнуть любой внутренний эндпоинт.

## Последствия

- Один транспорт на всю систему: отладка через `curl`, единые метрики и трейсы
- Circuit breaker обязателен: без него падение `catalog` вызывает лавину
  зависших запросов в `booking`
- Сервисный токен нужно обновлять по истечении — это часть клиента в `libs/common`
- При росте числа синхронных вызовов решение стоит пересмотреть
