# ADR-0015. Миграции — k8s Job по Helm-хуку

**Статус:** принято, 02.09.2026

## Контекст

Схему базы нужно обновлять при выкладке. Сервис работает в нескольких репликах,
и запуск миграции в каждой реплике приводит к гонке.

## Решение

Миграции выполняет отдельный k8s Job, запускаемый Helm-хуком до обновления
Deployment:

```yaml
annotations:
  "helm.sh/hook": pre-install,pre-upgrade
  "helm.sh/hook-weight": "-5"
  "helm.sh/hook-delete-policy": before-hook-creation
```

Приложение при старте выполняет `alembic current`, сравнивает с `alembic heads`
и **падает при расхождении**, а не работает на несовместимой схеме.

Правило: только совместимые вперёд изменения. Удаление колонки — две выкладки:
сначала код перестаёт её читать, затем миграция удаляет.

## Альтернативы

**InitContainer в каждом поде.** Просто и без хуков, но при трёх репликах три
параллельных `alembic upgrade` борются за блокировку; первый выигрывает,
остальные ждут или падают.

**Миграция при старте приложения.** Самый быстрый путь и худшая идея: гонки между
репликами, долгий старт, падение readiness при тяжёлой миграции, невозможность
откатить выкладку без отката схемы.

## Последствия

- Миграция выполняется ровно один раз независимо от числа реплик
- Неудачная миграция останавливает выкладку до обновления подов —
  старая версия продолжает работать
- Приложение никогда не стартует на схеме, которую не понимает
- Долгая миграция блокирует выкладку; для учебных объёмов несущественно
