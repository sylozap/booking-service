# ADR-0004. Transactional outbox + собственный relay

**Статус:** принято, 02.09.2026

## Контекст

Сервис меняет состояние в своей базе и должен опубликовать событие в Kafka.
Две операции в разных системах не могут быть атомарными: при падении между ними
либо изменение есть, а события нет, либо наоборот.

## Решение

Событие пишется в таблицу `outbox` **в той же транзакции**, что и изменение
состояния. Отдельная asyncio-задача в составе того же сервиса (relay) читает
неопубликованные записи, публикует их в Kafka и проставляет `published_at`:

```sql
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY created_at LIMIT 100
FOR UPDATE SKIP LOCKED;
```

`FOR UPDATE SKIP LOCKED` позволяет нескольким репликам работать параллельно
без дублирования работы.

## Альтернативы

**Debezium + Kafka Connect (CDC по WAL).** Продакшн-грейд, не требует relay-кода
и гарантирует порядок. Но это два тяжёлых компонента в кластере, заметная настройка
и ещё один источник отказов на локальном стенде.

**Публикация из хендлера после коммита.** Просто, но при падении между коммитом
и `publish` событие теряется навсегда. Неприемлемо.

## Последствия

- Гарантия «изменение есть ⇔ событие ушло» без внешних компонентов
- Доставка at-least-once: при падении между публикацией и отметкой сообщение
  уйдёт повторно, что гасится дедупликацией консьюмера
- Нужны метрики `outbox_pending_messages` и `outbox_publish_lag_seconds`
  и алерт на непустеющий outbox — иначе тихо вставший relay незаметен
- Таблица `outbox` требует периодической чистки опубликованных записей
- API не ждёт Kafka: ответ клиенту отдаётся сразу после коммита
