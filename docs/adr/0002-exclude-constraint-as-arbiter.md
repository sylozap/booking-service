# ADR-0002. EXCLUDE USING gist как единственный арбитр занятости

**Статус:** принято, 02.09.2026; пересмотрено 17.10.2026 — `occupied_range` не генерируемый столбец

## Контекст

Центральное требование домена: мастер не может быть занят двумя записями
одновременно. Занятость записи — это интервал `[start_at, end_at + buffer)`.
Длительность услуги переменная, поэтому конфликтом является любое пересечение
интервалов, а не совпадение времени начала.

Система работает в нескольких репликах, запросы конкурентны.

## Решение

Инвариант защищается ограничением PostgreSQL:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT no_overlapping_bookings
EXCLUDE USING gist (
    master_id      WITH =,
    occupied_range WITH &&
) WHERE (status IN ('pending','confirmed','completed','no_show'));
```

Нарушение приходит как SQLSTATE `23P01` и транслируется в `409 slot_taken`
со списком ближайших свободных слотов. Никакой другой механизм — ни кэш,
ни блокировка, ни проверка в коде — арбитром не является.

## Альтернативы

**`UNIQUE(master_id, start_at)`.** Ловит только совпадение начала: записи
10:00–11:00 и 10:15–10:45 пройдут обе. Неприменимо при переменной длительности.

**Проверка в коде под `SELECT ... FOR UPDATE`.** Работает, пока все пути записи
дисциплинированно берут блокировку. Инвариант живёт в приложении и ломается
при первом же новом пути (импорт, админка, миграция данных).

**Транзакции `SERIALIZABLE`.** Корректно, но даёт ошибки сериализации под нагрузкой
и требует ретраев на каждом пути записи; при этом инвариант всё равно
не выражен явно в схеме.

## Последствия

- Гонка разрешается базой, а не приложением; приложение только переводит
  ошибку в понятный клиенту ответ
- Отменённые записи автоматически освобождают время: они вне частичного условия
- Ограничение создаёт gist-индекс, который заодно ускоряет проверку пересечений
  в запросе доступности
- Требуется расширение `btree_gist`
- Столбец `occupied_range` вычисляется как генерируемый; если версия PostgreSQL
  откажет в `IMMUTABLE`, он становится обычным столбцом, заполняемым в модели.
  Инвариант при этом не меняется
- Тест гонки (N параллельных запросов → ровно один `201`) обязателен

## Пересмотр (17.10.2026)

**Что изменилось.** Сработал запасной вариант из «Последствий»: `occupied_range` —
обычный столбец `tstzrange`, который заполняет модель SQLAlchemy, а разойтись
со временем брони ему не даёт `CHECK (occupied_range = tstzrange(start_at,
end_at + make_interval(mins => buffer_min), '[)'))` (`occupied_range_matches_times`).

**Почему.** Проверка до логики (`3e349c7`, `test_exclusion_spike.py`):
PostgreSQL 17 отвечает `generation expression is not immutable` — оператор
`timestamptz + interval` помечен `STABLE`. Проверочное ограничение `STABLE`
допускает, поэтому арбитром по-прежнему остаётся база, а не дисциплина путей
записи. Само решение — `EXCLUDE USING gist` по активным статусам
(`ex_bookings_no_overlapping`) — не изменилось.
