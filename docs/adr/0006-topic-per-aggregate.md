# ADR-0006. Топик на агрегат, тип события внутри конверта

**Статус:** принято, 02.09.2026

## Контекст

Нужно выбрать гранулярность топиков Kafka. Основное требование домена: события
одной сущности должны обрабатываться в порядке их возникновения.

## Решение

Топик на агрегат, с версией схемы в имени:

```
auth.users.v1           catalog.masters.v1      catalog.services.v1
booking.bookings.v1     booking.reminders.v1    <topic>.dlq
```

Тип события (`booking.created`, `booking.cancelled`, ...) лежит в конверте
и дублируется в заголовке сообщения. Ключ партиционирования — id агрегата,
поэтому все события одной сущности попадают в одну партицию и строго упорядочены.

Ломающее изменение схемы = новый топик `.v2`, период двойной публикации,
миграция консьюмеров, отключение `.v1`.

## Альтернативы

**Топик на каждый тип события.** Удобная подписка «только на нужное», но порядок
между `booking.created` и `booking.cancelled` для одной брони не гарантирован:
отмена может обогнать создание, и консьюмер получит отмену несуществующей записи.
Это реальный баг, а не теоретический.

**Один топик на всю систему.** Минимум конфигурации, но все консьюмеры читают всё
и фильтруют; масштабирование и лаг-метрики становятся бессмысленными.

**Версия только внутри конверта, топик один навсегда.** Меньше топиков,
но консьюмер вынужден одновременно поддерживать все версии схемы.

## Последствия

- Порядок событий одной сущности гарантирован
- Консьюмер обязан игнорировать незнакомые `event_type`, а не падать на них
- 3 партиции на топик локально; при росте число партиций можно увеличивать —
  ключ агрегата сохранит порядок
- Версия в имени топика делает миграцию схемы наблюдаемой: видно, кто ещё читает `.v1`
