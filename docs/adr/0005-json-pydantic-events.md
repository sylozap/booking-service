# ADR-0005. JSON + Pydantic-схемы вместо Avro и Schema Registry

**Статус:** принято, 02.09.2026

## Контекст

Событиям нужен формат сериализации и способ контролировать совместимость схем
между продюсером и консьюмерами.

## Решение

События сериализуются в JSON. Схемы конверта и всех `payload` — Pydantic-модели
в `libs/common/events`, общие для продюсера и консьюмера. Клиент Kafka — `aiokafka`.

Совместимость держится дисциплиной: добавление необязательного поля увеличивает
`event_version`, ломающее изменение порождает новый топик `.v2`
([ADR-0006](0006-topic-per-aggregate.md)).

## Альтернативы

**Avro + Confluent Schema Registry.** Настоящая проверка совместимости схем
на стороне брокера, компактная бинарная сериализация. Но это плюс один компонент
в кластере, синхронный клиент `confluent-kafka` в async-коде и заметно более
тяжёлая отладка: сообщение нельзя прочитать глазами.

**JSON Schema + Schema Registry.** Компромисс: читаемо и совместимость проверяется.
Всё ещё плюс один компонент ради проекта с пятью типами событий.

**FastStream поверх aiokafka.** Существенно меньше кода: роутеры, DI, ретраи
из коробки. Но фреймворк прячет ровно ту механику (коммит оффсетов, дедупликация,
DLQ), ради которой Kafka и берётся в учебный проект.

## Последствия

- Сообщения читаются глазами в любой консоли — отладка проще
- Схемы типизированы и переиспользуются: рассогласование ловится `mypy`
- Монорепо усиливает это решение: обе стороны импортируют одну модель
- Плата: нет автоматической проверки совместимости, ответственность на разработчике
- Если проект вырастет за пределы монорепо, Schema Registry станет необходим
