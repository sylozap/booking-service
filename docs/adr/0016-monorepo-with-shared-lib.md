# ADR-0016. Монорепо с общей библиотекой libs/common

**Статус:** принято, 02.09.2026

## Контекст

Пять сервисов с почти одинаковой обвязкой: конфигурация, логирование, трассировка,
формат ошибок, клиент Kafka, проверка JWT, outbox и relay. Проект ведёт один
разработчик.

## Решение

Монорепозиторий. Каждый сервис — отдельный Docker-образ и отдельный Helm-релиз,
то есть остаётся независимо деплоимым. Общая обвязка вынесена в `libs/common`
и ставится как локальный пакет.

```
services/  api-gateway/ auth/ catalog/ booking/ notification/
libs/      common/
deploy/    helm/ compose/
docs/
```

В `libs/common` живут в том числе **Pydantic-схемы всех событий** — один источник
правды для продюсера и консьюмера ([ADR-0005](0005-json-pydantic-events.md)).

## Альтернативы

**Репозиторий на сервис.** Как в больших командах: полная независимость,
версионирование через пакеты. Для одного разработчика это чистый оверхед —
пять репозиториев, пять CI, публикация общей библиотеки в реестр при каждом
изменении.

**Монорепо с полным дублированием обвязки.** «Честная» независимость сервисов,
но одна и та же логика пишется пять раз и расходится на третий месяц.

## Последствия

- Изменение схемы события ловится `mypy` сразу на обеих сторонах
- CI собирает только изменённые сервисы, а не всё подряд
- Риск: `libs/common` может превратиться в свалку. Правило — туда попадает только
  то, что нужно минимум трём сервисам и не содержит доменной логики
- Общая библиотека создаёт связность при выкладке: ломающее изменение в ней требует
  пересборки всех сервисов
