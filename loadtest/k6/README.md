# Нагрузочный сценарий

`booking_flow.js` — час пик платформы глазами клиентов: смотрят свободное время,
открывают карточку мастера, часть из них записывается.

| Доля | Запрос | Что выбирается |
|---|---|---|
| 80 % | `GET /api/v1/availability` | случайная пара мастер × услуга, случайный день от завтра до +13 |
| 15 % | `GET /api/v1/masters/{id}/card` | случайный мастер |
| 5 % | `GET /api/v1/availability`, затем `POST /api/v1/bookings` | случайный **свободный** слот этого дня |

Профиль: разгон до 50 RPS за 2 минуты и 5 минут на этой скорости. Каждая операция
идёт своим сценарием `ramping-arrival-rate`, поэтому доли держатся точно,
сколько бы ни отвечала соседняя.

## Пороги

SLO оформлены как `thresholds`: если хоть один нарушен, k6 завершается с ненулевым
кодом.

| Метрика | Порог | Откуда |
|---|---|---|
| `http_req_failed` | < 1 % | доступность API 99 % |
| `http_req_duration{op:availability}` | p95 < 1 с | SLO поиска слотов |
| `http_req_duration{op:booking_lookup}` | p95 < 1 с | тот же запрос перед записью |
| `http_req_duration{op:create_booking}` | p95 < 500 мс | SLO создания брони |
| `http_req_duration{op:card}` | p95 < 2 с | своего SLO нет, порог только против явной деградации |
| `slot_conflicts` | < 20 % | защита сценария от вырождения в тест конфликтов |

`409 slot_taken` ошибкой не считается: слот могли занять между просмотром
и записью, и платформа обязана ответить именно так. Конфликты считаются
отдельно, в `slot_conflicts`. Если их много, сценарий меряет гонку за слоты,
а не запись.

## Клиенты

Все запросы идут от имени клиентов из `users.json`. Без этого нагрузку не дать:
gateway пускает с одного адреса 30 анонимных запросов в минуту, а k6 — это один
адрес. Пользователю разрешено 120 запросов в минуту и 5 броней в минуту. При
100 клиентах и 50 RPS на каждого приходится около 30 запросов и 1,5 брони
в минуту.

Демо-клиенты seed не годятся: у них нет известного пароля и подтверждённой почты.
`make loadtest-users` регистрирует `load-001…load-100@load.barber.example` напрямую
в auth (через port-forward, в обход лимита регистраций на gateway), подтверждает
адреса по письмам из лога notification и логинит каждого. В `users.json` пишутся
пароль и свежий access-токен на клиента. Повторный запуск ничего не создаёт,
только заново выдаёт токены.

Токены выдаются до k6, а не в его `setup()`: вход через gateway — анонимный
запрос, 30 в минуту с адреса, и сотня входов заняла бы четыре минуты.
`make loadtest` сам выполняет этот шаг перед каждым прогоном.

**Прогон не может длиться дольше 15 минут** — столько живёт access-токен. После
этого все запросы получат `401`, и порог `http_req_failed` упадёт.

## Запуск против kind

```bash
make kind-up OBSERVABILITY=1   # платформа с метриками; без них нет графиков HPA и p95 по сервисам
make loadtest                  # 7 минут; отчёт в stdout и results/summary-<время>.json
```

k6 запускается из образа `grafana/k6`, ставить его не нужно. Профиль меняется
переменными: `make loadtest RATE=20 RAMP=30s HOLD=1m`.

`users.json` и `results/` в git не попадают: в первом пароль, во втором цифры
конкретного стенда.

## Что смотреть во время прогона

- `kubectl get hpa -n barber -w` — масштабирование gateway и booking.
- Grafana (`make kind-grafana`) — дашборды сервисов, p95 доступности по
  `source` (кэш или база), отставание outbox.
